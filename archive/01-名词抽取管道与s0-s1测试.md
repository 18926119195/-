# 一、架构说明（ARCHITECTURE_v2.md）

## 核心流程概览

```
纯文表 → s0规则抽取 → 截断构建 → s1补缺LLM → 合并审查LLM → 终词表 → 去重 → 相关性 → 拓扑链 → 召回
```

## 1. 纯文表 (PureTextTable)

**职责**：从原始材料提取纯文本，去除格式、标记、元数据。

**输出**：
- `fullText`: 完整纯文本
- `sourceNote`: 来源标注

## 2. s0 规则名词表 (NounS0Table)

**职责**：规则抽取 + 全局偏移量定位

**核心特性**：
- 规则识别：大写开头词、CJK 2-4字、词频>=2
- **全局偏移量**：记录每个名词在纯文表中的精确位置 `{start, end}`
- 去重：标准化ID（小写+去空格）
- 子串剪枝：CJK短词包含在长词中时剪除

**输出**：
```typescript
type NounS0Entry = {
  id: string                              // 标准化ID
  surface: string                         // 展示形式
  df: number                              // 文档频率
  offsets: Array<{start, end}>            // 全局偏移量列表
}
```

## 3. 截断构建 (Truncations)

**职责**：识别 s0 名词之间的间隙文本

**截断定义**：
- **左边界**：左侧 s0 名词ID（或 'START'）
- **右边界**：右侧 s0 名词ID（或 'END'）
- **偏移量**：`{startOffset, endOffset}` 在纯文表中的位置
- **文本**：截断的实际内容（用于 LLM）

**用途**：提供给 s1 补缺 LLM，递归提取遗漏的名词。

## 4. s1 补缺 LLM (NounS1FillTable)

**职责**：递归提取截断中的遗漏名词

**流程**：
1. 对每个截断调用 LLM：`extract_nouns_from_truncation(truncation.text)`
2. LLM 返回：`[{noun, relativeStart, relativeEnd}, ...]`
3. **偏移量计算**：`globalStart = truncation.startOffset + relativeStart`
4. 递归：如果提取出新名词，重新构建该区域的截断并继续提取

**输出**：
```typescript
type NounS1Entry = {
  id: string
  surface: string
  sourceType: 'llm_fill'
  df: number
  offsets: Array<{start, end}>            // 全局偏移量
}
```

**关键设计**：
- **递归终止条件**：最大深度=3 或 单次提取为空
- **批处理**：按截断批量并行调用 LLM
- **容错**：LLM 失败时标记但不阻塞流程

## 5. 合并审查 LLM (NounMergeTable)

**职责**：检查终词表中相邻名词是否应该合并为复合名词

**终词表定义**：`s0 + s1` 合并后的所有名词

**合并条件**：
- **位置相邻**：在终词表排序后相邻（按 `firstOffset.start` 排序）
- **偏移连续**：存在至少一对偏移满足 `left.end == right.start` 或间隙 <= 1
- **LLM 判断**：`should_merge(left, right) → {should_merge: boolean, merged_surface?: string}`

**流程**：
1. 构建相邻对候选列表
2. 批量调用 LLM 审查
3. 合并操作：创建新条目，继承偏移量，标记 `merged_from`

**输出**：
```typescript
type MergedNoun = {
  id: string
  surface: string
  sourceType: 'merged'
  merged_from: [string, string]           // 原始两个名词ID
  df: number
  offsets: Array<{start, end}>
}
```

## 6. 终词表 (FinalNounTable)

**构成**：`s0 + s1 + merged` 合并去重

**去重规则**：
- 如果两个名词完全重叠（偏移量相同），保留 `merged > s1 > s0` 优先级高的
- 标准化ID相同时合并 `offsets`

**输出**：
```typescript
type FinalNounEntry = {
  id: string
  surface: string
  sourceType: 'rule' | 'llm_fill' | 'merged'
  df: number
  offsets: Array<{start, end}>
}
```

## 7. 相关性评分 (RelevanceScoring)

**职责**：用户问题 vs 终词表名词相关性

**方法**：
1. 用户输入：`query`
2. 批量调用 LLM：`rate_relevance(query, noun) → score ∈ [0, 10]`
3. 过滤：`score >= threshold` (默认 5)

**输出**：
```typescript
type RelevantNoun = {
  id: string
  surface: string
  relevance_score: number
}
```

## 8. 拓扑链构建 (TopologyChain)

**职责**：基于终词表中名词的**相邻关系**构建拓扑链

**相邻定义**：
- 在终词表中按 `firstOffset.start` 排序
- 名词A和名词B相邻 = 排序后索引差 <= 2（±2 窗口）

**拓扑链定义**：
- 从一个高相关性名词出发
- 沿着相邻关系递归扩展
- **最多5个名词**
- 按偏移量顺序排列

**流程**：
1. 种子：相关性分数 Top-K 的名词
2. 对每个种子 BFS 扩展：收集相邻名词（±2 窗口）
3. 截断到5个名词
4. 构建链：`[n1, n2, n3, n4, n5]`

**输出**：
```typescript
type TopologyChain = {
  chain_id: string
  nouns: string[]                         // 名词ID列表（5个）
  seed_noun: string                       // 种子名词ID
  note: string
}
```

## 9. 召回 (Recall)

**职责**：基于拓扑链定位原文区间

**方法**：
- 链首名词：`firstNoun.offsets[0].start`
- 链尾名词：`lastNoun.offsets[0].end`
- 召回文本：`fullText.slice(start, end)`

**输出**：
```typescript
type RecallChunk = {
  chain_id: string
  text: string
  start_offset: number
  end_offset: number
  nouns: string[]
}
```

## 关键设计决策

### 1. 为什么需要全局偏移量？

**问题**：s0 规则抽取会遗漏大量名词，需要补缺 LLM。但补缺的名词必须知道在原文中的位置，才能：
- 与 s0 名词合并去重
- 构建相邻关系（拓扑链）
- 精确召回原文区间

**解决方案**：
1. s0 记录每个名词的全局偏移量 `{start, end}`
2. 截断记录自己的全局偏移量 `{startOffset, endOffset}`
3. s1 LLM 返回相对偏移 → 转换为全局偏移

### 2. 为什么需要截断（Truncations）？

**问题**：s0 规则抽取后，名词之间有大量间隙文本，这些文本中可能包含重要名词（如动词转名词、小写专有名词）。

**解决方案**：
- s0 名词视为"已知锚点"（mask）
- 截断 = 锚点之间的间隙
- 补缺 LLM 专注于提取截断中的遗漏名词
- 递归：提取新名词后再次构建截断

### 3. 为什么需要合并审查 LLM？

**问题**：
- s0 规则："machine", "learning" → 两个独立名词
- 实际："machine learning" 应该是一个复合名词

**解决方案**：
- 合并审查 LLM 检查终词表中相邻且偏移连续的名词对
- 判断是否应该合并为复合名词
- 创建新的 merged 条目

### 4. 为什么拓扑链基于相邻关系？

**假设**：原文中相邻的名词（在终词表排序中相邻）通常有语义关联。

**方法**：
- ±2 窗口：每个名词可以连接到前后各2个名词
- BFS 扩展：从高相关性种子出发，沿相邻关系扩展
- 5个名词：既能覆盖足够上下文，又不至于过长

**优势**：
- 无需 LLM 判断名词对关系（成本高）
- 基于位置的启发式，简单高效
- 5词链自然包含上下文

## 实现注意事项

### 并行化

- **s1 补缺 LLM**：按截断批量并行（concurrency=10）
- **合并审查 LLM**：按相邻对批量并行（concurrency=10）
- **相关性评分**：按名词批量并行（concurrency=20）

### 容错

- LLM 调用失败时：记录错误，继续后续流程
- 偏移量计算错误时：跳过该名词，记录警告
- 递归深度限制：防止无限循环

### 调试

- 每个阶段输出 `note` 字段，记录统计信息
- 终词表保留 `sourceType`，追溯来源
- 合并名词保留 `merged_from`，可逆向查询

# 二、s1 三大改进说明（README-s1-improvements.md）

## 问题背景

三个关键问题：

1. **限流问题**：哪里可以看到限流？如何处理 API 限流？
2. **防污染问题**：±50 字符上下文窗口会不会重复提取 s0 已经覆盖的名词？
3. **位置准确性问题**：多个截断送进同一个 LLM，返回的名词能否准确定位到真实位置？

## 1. 限流处理（429 重试 + 指数退避）

### DeepSeek API 限流参数（参考）

根据 DeepSeek API 文档，常见限流如下：

- **免费用户**：10 RPM（每分钟请求数）
- **付费用户**：取决于套餐，通常 100-500 RPM

### 实现方式

`s1-llm-fill.js` 已实现：

```javascript
async function callLLM(prompt, signal, retryCount = 0) {
  const MAX_RETRIES = 3;
  const BASE_DELAY = 2000; // 初始延迟2秒
  
  try {
    const response = await fetch(...);
    
    // 检测 429 限流
    if (response.status === 429 && retryCount < MAX_RETRIES) {
      const delay = BASE_DELAY * Math.pow(2, retryCount); // 指数退避：2s → 4s → 8s
      console.warn(`[429限流] 等待 ${delay}ms 后重试 (${retryCount + 1}/${MAX_RETRIES})...`);
      await new Promise((resolve) => setTimeout(resolve, delay));
      return callLLM(prompt, signal, retryCount + 1);
    }
    
    // ... 正常处理
  } catch (err) {
    // 网络错误也重试（例如连接超时）
    if (retryCount < MAX_RETRIES) {
      const delay = BASE_DELAY * Math.pow(2, retryCount);
      console.warn(`[网络错误] ${err.message}，等待 ${delay}ms 后重试...`);
      await new Promise((resolve) => setTimeout(resolve, delay));
      return callLLM(prompt, signal, retryCount + 1);
    }
    throw err;
  }
}
```

**关键点**：
- 遇到 `429 Too Many Requests` 时自动重试 3 次
- 每次重试延迟翻倍（2s → 4s → 8s），避免持续触发限流
- 并发数 `CONCURRENCY=5` 已经比较保守，避免瞬时请求过多

### 如何查看限流

**运行时输出**：当触发 429 时，终端会打印：
```
[429限流] 等待 2000ms 后重试 (1/3)...
```

**API 响应头**：大部分 OpenAI 兼容 API 会返回限流头信息：
```
X-RateLimit-Limit-Requests: 100
X-RateLimit-Remaining-Requests: 0
X-RateLimit-Reset-Requests: 30s
```

## 2. 防污染：过滤 s0 已覆盖的名词

### 问题描述

`locateNounInFullText` 在截断位置 ±50 字符内搜索名词。如果这个上下文窗口覆盖了 s0 已经提取过的区域，会导致：
- LLM 提取的名词实际上已经在 s0 里了
- 最终 s0+s1 合并时会出现重复记录

### 解决方案

#### 步骤 1：`validate-s0-quality.js` 输出 s0 命中区间表

```json
{
  "hits": [
    { "surface": "理论", "start": 100, "end": 102 },
    { "surface": "système", "start": 150, "end": 157 }
  ]
}
```

#### 步骤 2：`s1-llm-fill.js` 加载 s0 区间并过滤重叠位置

```javascript
function locateNounInFullText(noun, fullText, truncStart, truncEnd, contextWindow = 50, s0HitIntervals = []) {
  // ... 搜索逻辑 ...
  const overlapsS0 = s0HitIntervals.some((interval) => {
    return !(globalEnd <= interval.start || globalStart >= interval.end);
  });
  if (!overlapsS0) {
    offsets.push({ start: globalStart, end: globalEnd });
  }
}
```

**结果**：如果 LLM 提取的名词位置与 s0 已有区间重叠，直接跳过，不记录到 s1 结果。

## 3. 位置准确性：批量请求的名词定位机制

### 问题描述

当 8 个截断合并到一个 LLM 请求中，LLM 返回带 `trunc_id` 的名词列表。**疑问**：如果 LLM 搞混了截断归属，会不会导致位置定位错误？

### 解决方案：两级定位 + 置信度标记

1. LLM 返回 `trunc_id`，明确标注名词来自哪个截断
2. 根据 `trunc_id` 查找原始截断的起始位置
3. 在截断 ±50 字符窗口内搜索名词
4. 计算全局偏移量，并标记置信度：
   - **`high`**：位置完全落在原始截断范围内
   - **`medium`**：位置在 ±50 字符上下文窗口内
   - **`low`**：位置在全文其他地方找到（可能 LLM 混淆）

### 输出报告

```
位置置信度: 高=256, 中=42, 低=8
```

## 总结

| 问题 | 解决方案 | 效果 |
|------|---------|------|
| 限流 | 429 自动重试 + 指数退避 | 遇到限流时自动等待，无需手动干预 |
| 防污染 | 加载 s0 区间表，过滤重叠位置 | s1 只包含真正新增的名词，不重复 s0 |
| 位置准确性 | 两级定位 + 置信度标记 | 可验证每个名词的定位质量，识别 LLM 混淆 |

# 三、s1 LLM 补缺脚本使用指南（README-s1-llm-fill.md）

## 核心策略

针对 **s0 (spaCy) 未覆盖的疑似漏词截断**，使用 LLM 补缺提取名词，并保留精确位置索引。

### 提速设计

1. **批量合并** (`BATCH_SIZE=8`)：将多个短截断合并到一个 LLM 请求中
2. **并行批处理** (`CONCURRENCY=5`)：同时发起 5 个 LLM 请求
3. **精确位置索引**：每个名词记录其在纯文表中的全局偏移量 `{start, end}`，带上下文窗口（±50字符）优先搜索截断附近区域

### LLM 注意力保护

1. **结构化提示词**：明确标注每个截断的编号和位置，要求返回严格 JSON 格式（带 `trunc_id` 映射）
2. **独立处理原则**：每个截断的提取结果独立标注，输出时通过 `trunc_id` 回溯到原始截断位置
3. **温度设置**：`temperature=0.1`（低温模式）：减少随机性，提高提取一致性

## 用法

```powershell
$env:LLM_PROVIDER="openai"
$env:OPENAI_API_KEY="sk-xxxxx"
$env:LLM_MODEL="gpt-4o-mini"
$env:LLM_CONCURRENCY="5"
$env:BATCH_SIZE="8"
node s1-llm-fill.js
```

输出 `s1-nouns-with-offsets.json`：

```json
{
  "meta": {
    "source": "s1 LLM兜底补缺",
    "llmProvider": "openai",
    "model": "gpt-4o-mini",
    "concurrency": 5,
    "batchSize": 8,
    "inputTruncations": 369,
    "outputNouns": 127,
    "totalOffsets": 384,
    "elapsedSeconds": 18.3
  },
  "nouns": [
    {
      "id": "robotique",
      "surface": "robotique",
      "offsets": [
        { "start": 31004, "end": 31013 },
        { "start": 45821, "end": 45830 }
      ],
      "sourceTruncIds": [31004, 45821]
    }
  ]
}
```

## 性能估算

- **输入**：369 个疑似漏词截断
- **批量合并**：369 ÷ 8 = 47 批
- **并行处理**：47 ÷ 5 = 10 轮
- **预计耗时**：gpt-4o-mini 约 20 秒，claude-3-5-haiku 约 15 秒

## 验证质量

1. **覆盖率**：`outputNouns` 数量（预期 100-200 个新名词）
2. **命中率**：`totalOffsets / outputNouns`（预期 2-4 处/词）
3. **前10高频词**：控制台输出，人工审查是否为有效名词

# 四、s1 名词质量过滤规则验证报告（SUMMARY-s1-quality-filter.md）

## 过滤规则实现

在 `s1-llm-fill.js` 中新增 `isValidNoun()` 函数，在 `locateNounInFullText()` 定位前执行过滤：

### 过滤规则清单

1. **长度过短** (<3字符)，除非全大写缩写（如 AI、UN）
2. **纯标点/数字** 组合

# 七、s1 LLM 补缺准确率验证分析（ANALYSIS-s1-validation.md）

## 验证结果概览
- 样本数：20（疑似漏词截断）
- "完全一致"：16/20（80%）
- s1流程提取：7个名词
- 基准（单独询问）提取：3个名词
- 匹配：3个

## 关键发现：不一致的4个案例都是"s1多提，基准漏提"

| 截断文本 | s1流程 | 基准（单独询问） |
|---|---|---|
| "ouer homophonique" | homophonique | （空） |
| "créatrice et s" | créatrice | （空） |
| "-médiatique" | médiatique | （空） |
| "iaux, qualifiés par" | iaux | （空） |

**重要**：这4个词都是真实存在的法语单词，不是噪音。所以这不是"s1误提"，而是"基准方法漏提"。

## 根本原因：不是批量处理的问题，是两种prompt风格的差异

- **s1流程**：批量prompt，明确要求"提取所有名词性成分"，且截断带有±50字符上下文窗口辅助定位
- **基准方法**：单独询问，prompt风格是"这段文字是否包含名词"，面对极短、看起来不完整的碎片时，模型更倾向保守地判断"不确定/无法识别"而返回空

所以真实情况是：**基准方法本身对短碎片不够可靠**，不能作为衡量s1准确率的"金标准"。

## 结论：s1批量处理没有明显漏提问题

之前担心的"两次运行结果不同是因为批量处理漏提"这个假设，从这次验证看**不成立**。更可能的解释是：LLM在不同批次组合下对边界模糊的短词有轻微的判断波动（这在temperature=0.1下也会发生），但整体上s1的批量方式比单独询问更能抓住这些边界名词，而不是更差。

## 关于"多轮迭代"的建议

不需要用"连续两轮无新词才停止"的多轮迭代机制，因为：
1. 当前单轮结果已经比基准方法召回更多（7 vs 3）
2. 40个疑似漏词截断中，大部分（20个样本里有12个）双方都判定为空——这些确实是纯虚词/标点/连接词碎片，不是漏词
3. 多轮迭代主要解决的是"漏提"问题，但验证显示s1没有明显漏提，反而是基准方法漏提更严重

## 建议下一步

维持当前单轮方案，把重点放在：
1. 继续观察是否有真正的噪音词混入（目前过滤规则已生效，pl/pré未再出现）
2. 如果未来发现某些明显应该提取但两种方法都漏掉的名词，再针对性排查，而不是全面上多轮迭代机制（成本收益不成比例）

## 关键设计决策

### 1. 批量合并（Batch Merging）
369个截断，每8个合并到一个请求：网络请求369÷8=47次，提速8×

### 2. 并行批处理（Parallel Processing）
47批，并发5个Worker：并行轮次47÷5=10轮，提速5×。总提速8×5=40×

### 3. LLM 注意力保护（Attention Protection）
结构化提示词标注`[截断1]`、`[截断2]`；强制JSON输出`{"trunc_id": 1, "nouns": [...]}`；低温模式`temperature=0.1`；通过`trunc_id`精确定位到原始截断位置

### 4. 位置索引保留（Offset Preservation）
上下文窗口搜索（±50字符）；全局降级搜索（未找到时降级到全文搜索，限制5次）；精确偏移记录；去重合并

## 成本估算

- OpenAI gpt-4o-mini：约 $0.004（不到1分钱）
- Anthropic claude-3-5-haiku：约 $0.03（3分钱）

# 九、实验记录：纯文表/名词表前期数据清理（docs/EXPERIMENT-2026-09-16-data-cleaning.md）

日期：2026-09-16
范围：`docuverse_cartographies_squizoanalythiques_Fe_lix_Guattari` 语料的纯文表构建与 s0/s1 名词抽取管道

## 背景

纯文表（pure text table）是名词抽取管道的第一层产物：从 docuverse 的 chunk 集合里筛出"可检索原子"（`isRetrievableAtom`），拼接出 `atomSearchText`，再交给 s0（spaCy 规则）和 s1（LLM 补缺）抽取名词、生成 `final-noun-index.json`。这次的工作是排查并清理这一层里混进正文的非语言学噪声。

## 问题一：图脸占位说明混入正文

### 现象
`final-noun-index.json` 里出现 "Z-Library"、"p.39"、"Library" 等书源相关的"名词"，明显不是文本内容。

### 根因
`isRetrievableAtom` 用长度阈值（`< 24` 字符）判断是否跳过无 OCR 文字层的 `fig` 类型占位说明。但这类占位说明的固定模板本身超过24字符，绕开了长度过滤，被当成正文送进纯文表。s0规则据此把书源元数据当成名词提取了出来。

### 修复
在 `isRetrievableAtom` 中新增判断：若 chunk 为 `fig` 类型且无真实文字层（`faces.text` 不存在），且原始 `note` 命中 `/无文字层|未OCR/`，直接排除，不依赖长度阈值。

同步修改的文件：`src/core/text.ts`、`merge-s0-s1.js`、`validate-s0-quality.js`、`s1-llm-fill.js`、`merge-review-llm.js`

### 验证
- 可检索原子从1543降到1459（排除84个占位块）
- 抽查全部84个被排除的块，确认无一条包含真实版面内容
- "Z-Library"相关噪声全部清除

## 问题二：LaTeX/数学公式残留

### 现象
纯文表中有28处片段带公式残留，如`"$ \mathrm{F}^{i \mathrm{m}} $ Ts"`。`final-noun-index.json`中有168条名词条目是纯公式碎片，如`\Phi$.`（df:18）、`\varphi_1`（df:10）等。

### 根因
PDF→Markdown转换时，部分数学公式没有正确渲染，LaTeX源码直接残留在正文里。s0规则把`\varphi_1`、`\circ`等符号误判为"大写开头/带特殊字符的词"。

### 修复
在`atomSearchText`管道中新增`stripLatexResidue`（`stripHtmlTags`之后追加一步清理）：
1. 剥离完整的`$...$`/`$$...$$`数学环境
2. 剥离裸露的LaTeX命令序列（`\command`、`\command{...}`，允许一层嵌套花括号）
3. 清理残留孤立反斜杠
4. 清理残留的上下标花括号片段（`^{...}`、`_{...}`）

同步修改的文件：`src/core/text.ts`、`merge-s0-s1.js`、`validate-s0-quality.js`、`s1-llm-fill.js`、`merge-review-llm.js`

### 验证
- 修复后可检索原子从1459降到1447（排除12个纯公式块）
- 逐条核对这12个被排除的块：清理LaTeX语法后剩余文本`<4`字符，确认无真实语言内容损失
- 重跑`merge-s0-s1.js`生成新`final-noun-index.json`：LaTeX残留噪声从168条降到1条边缘案例（`^+$`，df:1）
